# 检索决策记录

## 2026-06-09：先使用 RRF 建立混合检索基线

### 决策

首个全文检索与向量检索融合方案使用 Reciprocal Rank Fusion（RRF）：

```text
RRF(document) = sum(1 / (k + rank_i(document)))
```

当前参数：

- `candidate_k = 5`：每路检索各取前 5 条候选；这是当前实验中最优且成本最低的配置。
- `rrf_k = 60`：降低头部名次差异的影响，优先奖励被两路共同召回的 FAQ。
- `top_k = 5`：返回最终前 5 条。

### 为什么先用 RRF，而不是固定加权

1. 全文检索的 `ts_rank` 与向量检索的余弦相似度量纲不同，直接执行
   `a * fulltext_score + b * vector_score` 没有可靠含义。
2. 固定加权需要先做分数归一化，并使用独立验证集选择权重；当前检索 300
   同时承担评估职责，直接在其上调权重会产生评估集过拟合。
3. RRF 只依赖排名，对分数分布和模型版本变化不敏感，适合作为低风险基线。
4. 当前单路结果互补：全文检索擅长精确词项，向量检索擅长同义表达。RRF 能直接
   验证这种互补是否真正改善最终排序。

### 边界与后续条件

- RRF 默认两路检索同等重要，弱检索源也可能把错误候选推高。
- 若 RRF 无法超过当前向量检索基线，应保留向量检索作为线上默认，不因“混合”
  名称强行上线 RRF。
- 只有在建立独立验证集，并完成分数校准后，才比较固定加权融合。
- 后续可比较：加权 RRF、归一化固定加权、cross-encoder reranker。

### Retrieval 300 实验结果

|方案|Recall@5|Top1 Accuracy|MRR@5|
|---|---:|---:|---:|
|全文检索|99.00%|90.00%|94.42%|
|向量检索|100.00%|**97.33%**|**98.61%**|
|RRF，`candidate_k=20, rrf_k=60`|100.00%|95.33%|97.51%|
|RRF，`candidate_k=10, rrf_k=60`|100.00%|95.67%|97.75%|
|RRF，`candidate_k=5, rrf_k=60`|100.00%|**95.67%**|**97.78%**|
|RRF，`candidate_k=20, rrf_k=10`|100.00%|95.33%|97.51%|
|RRF，`candidate_k=5, rrf_k=60`，向量优先打破平局|100.00%|**97.67%**|**98.78%**|

结论：

- 标准等权 RRF 保持了向量检索的 `Recall@5 = 100%`，但未超过向量单路的 Top1 和 MRR。
- 最优标准 RRF 修复了 2 条向量 Top1 错误，同时新增 7 条错误，净增加 5 条错误。
- `candidate_k` 从 20 降至 5 有小幅改善，说明全文深层候选会产生噪声。
- 修改 `rrf_k` 没有改善，主要矛盾不是排名衰减速度，而是两路质量不对称和
  `全文 rank1 / 向量 rank2` 与 `全文 rank2 / 向量 rank1` 的对称平分。
- 使用已被单路评估证明更强的向量排名打破 RRF 平局后，Top1 比向量单路增加 1 条，
  因此接入当前 Chat 原型。
- 当前混合检索串行执行，平均搜索耗时为 `23.28ms`，高于向量单路的 `14.67ms`；
  后续可并行执行全文与向量查询来降低延迟。

### 当前状态

当前 Chat Agent 使用 `candidate_k=5, rrf_k=60` 的 RRF，并仅在 RRF 分数相同时使用
向量排名打破平局。该参数是在 retrieval 300 上选择的，不能视为独立测试结论；
上线前需要新增留出集复验。下一轮优先评估轻量 reranker，而不是直接对原始异构
分数做固定加权。

## 2026-06-09：建立 retrieval holdout 300

### 为什么需要独立 holdout

`eval_retrieval_sample_300.jsonl` 已经用于比较全文、向量、RRF，并选择
`candidate_k=5`、`rrf_k=60` 和向量优先平局规则，因此它现在是开发集。继续在该集合
上报告最终效果会高估泛化能力。

### 隔离规则

- 从 retrieval 300 之外的 FAQ 中选取 300 条。
- 不仅排除开发集 FAQ ID，也按内容 hash 排除其完全重复副本。
- Holdout 内同一内容 hash 只生成一个测试问题，全部重复 ID 都标记为正确。
- 优先使用备用 FAQ 问法或不同标题，无法取得不同问法时才使用原问题。
- 按已有分类先覆盖，再固定随机补齐，避免结果被大量“未分类”FAQ 完全主导。
- Holdout 只用于最终复验，不再用于选择或修改 RRF 参数。

### 能力边界

该集合仍由当前知识库自动生成，只能称为“知识库内泛化测试”。真正的外部泛化测试
需要从新时间窗口的真实用户会话中抽样，并由独立标注确认正确 FAQ、应追问或应转人工。

### Holdout v1 冻结结果

本轮使用此前在 retrieval 300 上锁定的 RRF 参数直接测试，没有根据 holdout 调参：

|方案|Recall@5|Top1 Accuracy|MRR@5|Top1 正确数|
|---|---:|---:|---:|---:|
|全文检索|99.00%|94.67%|96.75%|284 / 300|
|向量检索|98.33%|95.33%|96.78%|286 / 300|
|RRF，锁定参数|**99.33%**|**96.33%**|**97.69%**|**289 / 300**|

开发集到 holdout 的 RRF 变化：

- Recall@5：`100.00% -> 99.33%`
- Top1 Accuracy：`97.67% -> 96.33%`
- MRR@5：`98.78% -> 97.69%`

结论：RRF 在未参与调参的知识库内 holdout 上仍优于两个单路检索，初步泛化通过。

但 holdout v1 暴露出两类数据质量问题：

- 备用问法切分产生了“（PC端）”“Resistance Line)”等残缺片段。
- “有教程吗”“如何操作”等缺少上下文的问题，不应强制要求命中某个指定 FAQ。
- 部分 FAQ 内容 hash 不同，但标题和语义近似；仅按完全重复扩展正确标签仍会产生假阴性。

因此 holdout v1 结果永久保留，不修改后重新宣称独立测试。后续建立 v2 时，应先过滤
低上下文片段，并对语义近重复进行独立标注；v2 作为新的测试集单独报告。
