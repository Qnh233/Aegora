# Engineering Journal

## 2026-09-04 — Governed flywheel evidence lineage

- **Objective / roadmap item**: establish the first governed-data-flywheel prerequisite without depending on the open Workflow, Redis or LiteLLM PRs.
- **Key design decisions / tradeoffs**: keep PostgreSQL/Strapi evidence storage unchanged; persist only stable Agent/Release identity into message metadata. Reflection may still analyze legacy rows, but it treats them as `legacy` and never clusters rows from different Agents together.
- **Pitfalls / root causes**: the existing configured runtime knew `agent_id` and `release_id` during execution but dropped that identity before chat persistence, so later reflection could mix semantically similar failures from unrelated Agents. This is a lineage loss, not a clustering-quality problem.
- **Highlights / reusable patterns**: normalize learning lineage once in `sessions.py`; carry `source_agent_id` plus bounded `source_trace_ids` into Skill draft metadata; partition embedding clustering by Agent before similarity grouping.
- **Important files / commands**: `services/runtime/apps/api_app.py`, `services/runtime/src/aegora_runtime/sessions.py`, `services/runtime/src/aegora_runtime/data_ops/reflection_flow.py`; targeted tests under `services/runtime/tests/test_sessions.py` and `test_skills.py`.
- **Verification / tests**: `29 passed` for targeted Runtime session/Skill tests; `python -m compileall -q services/runtime/src services/runtime/apps` passed; `git diff --check` passed. The local Anaconda environment initially lacked `psycopg` and `pocoflow`; both repository-declared dependencies were installed before rerunning the tests rather than masking import failures with stubs.
- **Blockers**: none for this phase. Existing PR #3 Python CI failure was independently confirmed as the known `main` pytest module-name collision already fixed in PR #1, so the fix was not duplicated here.
- **Next step**: add a per-Agent learning-policy contract that gates which evidence can produce proposals and which proposals may advance to evaluation/review.

## 2026-09-04 — Per-Agent learning-policy gate

- **Objective / roadmap item**: turn evidence lineage into an explicit Release-scoped learning contract so each Agent can independently control evidence capture and Skill proposal creation.
- **Key design decisions / tradeoffs**: keep the policy inside immutable Release configuration and persist a normalized snapshot with each chat turn. `capture_evidence` defaults to `true` so operational reports do not silently lose legacy visibility, while `propose_skills` defaults to `false` so autonomous learning is opt-in. `requires_human_review` defaults to `true`; promotion is intentionally not automated in this phase.
- **Pitfalls / root causes**: gating only at weekly-reflection execution time would make historical evidence semantics depend on whatever policy happens to be current later. Persisting the Release policy snapshot beside the evidence avoids that time-of-check/time-of-use drift. Mixed-policy rows inside one semantic cluster are handled conservatively: a Skill proposal is allowed only when every contributing evidence row permits it.
- **Highlights / reusable patterns**: normalize policy once in `runtime_context.py`; carry it through configured request persistence; filter disallowed evidence before both rule and embedding clustering; downgrade threshold-qualified but non-authorized clusters to `learning_review` instead of silently dropping them.
- **Important files / commands**: `services/runtime/src/aegora_runtime/runtime_context.py`, `services/runtime/apps/api_app.py`, `services/runtime/src/aegora_runtime/data_ops/reflection_flow.py`, targeted tests in `test_runtime_context.py` and `test_skills.py`; verification command: `python -m pytest services/runtime/tests/test_skills.py services/runtime/tests/test_runtime_context.py services/runtime/tests/test_sessions.py -q`.
- **Verification / tests**: `43 passed`; `python -m compileall -q services/runtime/src services/runtime/apps` passed; `git diff --check` passed.
- **Blockers**: no implementation blocker. Promotion/evaluation gates remain deliberately separate so they can be measured and reviewed before any automatic activation path exists.
- **Next step**: add an evaluation gate that records candidate evaluation results and prevents `source=agent` Skills from becoming active without explicit review criteria.

## 2026-09-04 — Agent Skill evaluation/promotion gate

- **Objective / roadmap item**: close the first executable-change gap in the governed flywheel by preventing Agent-generated Skill drafts from becoming production-active without evaluation evidence and a human reviewer.
- **Key design decisions / tradeoffs**: keep the gate in shared Runtime Skill-domain logic instead of only in one CLI path. Manual Skills remain compatible, while `source=agent` requires `metadata.evaluation.status=passed`, a dataset/version reference, non-empty metrics, evaluation timestamp, and `reviewed_by`. Evaluation evidence stays metadata-backed for now so the gate can ship before introducing a larger evaluation service/schema.
- **Pitfalls / root causes**: the existing reflection flow correctly created Agent Skills as `draft`, but Strapi could later set `lifecycle_status=active` and `sync_strapi_content.py` would trust that status. A CLI-only publish check would therefore be bypassable through the CMS synchronization path.
- **Highlights / reusable patterns**: one pure `agent_skill_promotion_errors()` function is reused by local promotion and Strapi sync; Strapi reviewer fields are now preserved into the PostgreSQL retrieval copy; the sync rejects invalid active Agent Skills before opening a database transaction.
- **Important files / commands**: `services/runtime/src/aegora_runtime/skills.py`, `services/runtime/scripts/skills.py`, `services/runtime/scripts/sync_strapi_content.py`, `services/runtime/tests/test_skills.py`, `services/runtime/tests/test_strapi.py`, `services/runtime/docs/operations.md`; targeted verification uses `python -m pytest services/runtime/tests/test_skills.py services/runtime/tests/test_strapi.py services/runtime/tests/test_runtime_context.py services/runtime/tests/test_sessions.py -q`.
- **Verification / tests**: targeted suite `50 passed`; `python -m compileall -q services/runtime/src services/runtime/apps services/runtime/scripts` passed; `git diff --check` passed. A local root-level `pytest -q` CI emulation progressed through the unit suite but stalled when reaching environment-dependent tests without the CI PostgreSQL service, so it was terminated rather than treated as a false failure; GitHub Actions remains the full-suite authority after push.
- **Blockers**: PR #4 received a GitHub Copilot CI-stabilization commit (`a4a6e2f`) after the prior local iteration. HTTPS fetch reset once; SSH/443 fetched the remote commit successfully. The local checkout must remain fast-forward/non-force when publishing this iteration.

## 2026-09-04 — Agent Skill evaluation evidence binding

- **Objective / roadmap item**: make the governed flywheel's promotion evidence reproducible and resistant to stale-evaluation reuse, closing the gap between the existing promotion gate and an automatically produced evaluation artifact.
- **Key design decisions / tradeoffs**: keep the existing Skill evaluator as the execution engine and add an optional evidence artifact for one unpublished candidate instead of introducing a new evaluation service. Evidence records the dataset SHA-256, exact candidate content hash, metrics, explicit pass criteria and UTC timestamp. Promotion now verifies the evidence content hash against the current Skill, so any post-evaluation edit forces reevaluation.
- **Pitfalls / root causes**: the previous gate accepted any `status=passed` evaluation metadata with metrics, which meant a Skill could be evaluated, edited afterward, and still carry stale passing evidence. The first local test command also mixed PowerShell/Unix environment syntax with `cmd.exe`; using DevSpace `workingDirectory` plus explicit `env` avoids shell-dependent false failures.
- **Highlights / reusable patterns**: cryptographically bind evaluation evidence to both dataset bytes and promotable content; treat evaluation as an immutable artifact rather than a mutable status flag; keep thresholds in the artifact so reviewers can reconstruct why a run passed.
- **Important files / commands**: `services/runtime/scripts/eval_skills.py`; `services/runtime/src/aegora_runtime/skills.py`; `services/runtime/tests/test_eval_skills.py`; `services/runtime/tests/test_skills.py`; targeted command `python -m pytest tests/test_skills.py tests/test_eval_skills.py -q` from `services/runtime` with `PYTHONPATH=src`.
- **Verification / tests**: targeted Skill/evaluation suite passed `24 passed`; broader runtime/static checks are run before commit. Documentation updated in both READMEs, `docs/migration.md`, and Runtime operations.
- **Blockers**: no implementation blocker. Because Strapi is the configured source owner for Skill content, the evaluator emits a review artifact rather than silently mutating PostgreSQL metadata behind Strapi's ownership boundary.
- **Next step**: add explicit canary/regression promotion criteria and a governed reviewer workflow that imports the signed/bound evaluation artifact through the content-owner path before activation.

## 2026-09-04 — Agent Skill regression promotion gate

- **Objective / roadmap item**: harden the governed flywheel so an Agent-generated Skill must prove it does not regress a previously accepted baseline before promotion; this advances the README quality-gate roadmap while keeping Canary rollout as a separate next phase.
- **Key design decisions / tradeoffs**: reuse the existing immutable evaluation artifact instead of adding a new service or database table. Promotion now requires explicit evaluation criteria plus `evaluation.regression.status=passed`. The evaluator accepts a previous accepted evidence artifact as the baseline and compares injection accuracy with a configurable maximum regression tolerance; absolute safety/misinjection thresholds remain independent gates.
- **Pitfalls / root causes**: the first regression unit test exposed normal binary floating-point noise (`0.95 - 1.0`), which would make audit JSON harder to review and compare. The artifact now rounds accuracy deltas to a stable precision. `rg` is not installed in this Windows environment, so repository search falls back to `git grep` rather than adding a dependency.
- **Highlights / reusable patterns**: combine absolute acceptance criteria with relative regression criteria; require a known-good evidence artifact before producing promotion-ready evidence; keep baseline dataset/content identifiers in the regression result for audit lineage.
- **Important files / commands**: `services/runtime/scripts/eval_skills.py`; `services/runtime/src/aegora_runtime/skills.py`; `services/runtime/tests/test_eval_skills.py`; `services/runtime/tests/test_skills.py`; targeted command `python -m pytest tests/test_skills.py tests/test_eval_skills.py -q` from `services/runtime` with `PYTHONPATH=src`.
- **Verification / tests**: targeted tests plus broader Runtime static checks are executed before commit; README, README_CN, migration and Runtime operations documentation are updated with the regression contract.
- **Blockers**: Canary still lacks real traffic/rollout evidence and should not be represented as implemented. PR #2/#3 Python CI remains dependent on the collection/environment fix already present on the current Flywheel branch/PR #4 until that fix lands on main.
- **Next step**: implement a first-class Canary evidence contract/runner or reviewer import path that can prove bounded production exposure before an Agent Skill becomes fully active.

## 2026-09-04 — Agent Skill Canary promotion contract

- **Objective / roadmap item**: close the next governed-flywheel promotion gap by requiring auditable Canary evidence before an Agent-generated Skill may become fully active.
- **Key design decisions / tradeoffs**: keep Canary as evidence under the existing immutable evaluation metadata rather than inventing a second lifecycle table. Promotion requires `evaluation.canary.status=passed`, an explicit `shadow` or `limited` mode, positive `sample_size`, non-empty metrics, observation time, and a Canary `content_hash` equal to the offline evaluation candidate hash. This turn deliberately validates the contract only; it does not pretend that a real traffic sampler already exists.
- **Pitfalls / root causes**: a generic `status=passed` Canary flag would be too weak and could be reused after candidate edits or attached without meaningful exposure. Binding the content hash and requiring non-zero exposure metadata makes stale/empty evidence fail closed while leaving the future rollout collector implementation independent.
- **Highlights / reusable patterns**: reuse the same content identity across offline evaluation, regression and Canary; make deployment mode explicit in evidence; keep promotion validation pure so both CLI publish and Strapi sync inherit the same rule automatically.
- **Important files / commands**: `services/runtime/src/aegora_runtime/skills.py`, `services/runtime/tests/test_skills.py`, `services/runtime/docs/operations.md`, both READMEs and `docs/migration.md`; targeted verification command: `python -m pytest services/runtime/tests/test_skills.py services/runtime/tests/test_eval_skills.py -q`.
- **Verification / tests**: broader governed-flywheel targeted suite (`test_skills.py`, `test_eval_skills.py`, `test_strapi.py`, `test_runtime_context.py`, `test_sessions.py`) passed `55 passed`; `python -m compileall -q services/runtime/src services/runtime/apps services/runtime/scripts` passed; `git diff --check` passed (only the existing Windows LF→CRLF working-copy warning was emitted).
- **Blockers**: no contract-level blocker. Real Canary evidence generation still needs a bounded shadow/limited traffic collector and acceptance criteria; until then the new gate intentionally prevents Agent Skill activation without externally supplied valid evidence.
- **Next step**: implement the bounded Canary evidence collector/runner, then define failure-rate/quality acceptance criteria that produce the validated contract from real exposure rather than manual metadata.
